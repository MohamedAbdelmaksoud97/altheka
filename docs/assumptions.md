# افتراضات وقرارات منصة العمليات القانونية

آخر تحديث: 2026-07-29

هذه الوثيقة تسجل قرارات المشروع الحالية. أي افتراض سابق يتعارض معها ملغى، ولا يوجد قرار تشغيلي حالي يمنع بدء الـMVP أو Sprint الأول.

## الهوية والوصول

- توجد رحلتان منفصلتان للتسجيل: عميل وموظف.
- الموظف الجديد يبقى بحالة `pending_staff_approval` ولا يحصل على وصول تشغيلي حتى يحدد مدير النظام الإدارة والمسمى والأدوار.
- العميل بحالة `client_waiting` يستطيع إنشاء الطلب ورفع مستنداته، ويتحول إلى `active_client` عند ربط مدير العملاء أول طلب بملفه.
- «مساعد إدارة التقاضي» و«سكرتير إدارة التقاضي» مسمى وظيفي واحد داخل النظام.
- النظام هو المصدر التشغيلي الوحيد للمحادثات والمستندات وسير العمل؛ لا يوجد تكامل WhatsApp أو Google Drive أو «المحامي الذكي».
- اعتماد العقد يسجل داخل النظام مع نسخة العقد وبصمتها والمستخدم والوقت وIP وUser Agent.
- الإشعارات داخل النظام وبالبريد. لا توجد MFA أو SMS أو WhatsApp في الـMVP.
- **Needs Client Confirmation:** النطاق النهائي، Redirect URLs، بريد مدير النظام الأول، SMTP، وبيانات المرسل مطلوبة قبل Staging وليست مانعًا للتطوير.

## أطراف الإجراء

- لكل إجراء أربعة أطراف مستقلة: `responsible`, `executor`, `follower`, `approver`.
- القالب يخزن قاعدة اختيار من دور أو مسمى وظيفي أو عضوية مشروع أو اختيار يدوي، ولا يخزن مستخدمًا بعينه.
- التنفيذ يقبل موظفًا واحدًا أو عدة موظفين؛ المسؤول والمعتمد فرديان افتراضيًا.
- عند عدم حسم المنفذ تصبح الحالة `awaiting_assignment`.
- قواعد القالب Defaults قابلة للتعديل، وتتحول عند التشغيل إلى مشاركين فعليين مع Audit كامل لإعادة الإسناد.
- ما قبل التعاقد: مدير العملاء مسؤول، والمكلف بالدراسة منفذ، ومدير العملاء أو موظف معين متابع، ومدير التقاضي أو التركات معتمد.
- التقاضي: مدير التقاضي مسؤول ومعتمد، والمحامي أو الأخصائي منفذ، وسكرتير التقاضي متابع.
- التركات: مدير التركات مسؤول ومعتمد، وسكرتير التركات متابع، والتنفيذ يقبل عضوًا أو أكثر ويمكن للمدير أو السكرتير تكليف نفسيهما.
- الماليات والإقفال: المحاسب منفذ مالي، ومدير الإدارة مسؤول، والسكرتير أو مدير المشروع متابع، والمدير التنفيذي يعتمد فقط عند الحاجة لاعتماد أعلى.
- **Needs Client Confirmation:** مصفوفة العمليات التي تستوجب اعتماد المدير التنفيذي ستظل قابلة للضبط حتى اعتمادها رسميًا.

## المدد والتوازي

- `planned_duration` مدة الإجراء، و`target_duration` و`maximum_duration` حدود المرحلة؛ لا تجمع مدد الإجراءات حسابيًا.
- الإجراءات غير المرتبطة تعمل بالتوازي، وترتبط الإجراءات المتتابعة بـDependencies صريحة.
- تجاوز المرحلة ينشئ تنبيهًا وتصعيدًا ولا يغلقها أو يوقفها.
- الحصر والاستعلام حد أقصى 60 يومًا من اكتمال المستندات والوكالات.
- التهيئة مستهدفة خلال 60 يومًا وتعمل على مستوى كل أصل.
- الحراسة وتقاضي التركة مساران اختياريان متوازيان.
- التصفية والتسويق مستهدفان خلال 90 يومًا لكل أصل أو مجموعة أصول، ولا تضاف المدتان تلقائيًا.
- لكل `estate_asset` Workflow فرعي مستقل، لذلك يمكن أن تكون أصول التركة في مراحل مختلفة.
- **Needs Client Confirmation:** قواعد حساب يوم العمل والعطلات والتصعيد المتدرج قبل الإنتاج.

## رؤية العميل

- الرؤية الافتراضية `internal`، ولا يصل المحتوى للعميل إلا إذا أنشئ في قناة العميل أو نشر صراحة.
- القيم هي `internal`, `client_visible`, `requires_client_action`.
- المستند الحساس يحتاج `client_visibility_status = published` إضافة إلى مستوى الرؤية، مع ناشر ووقت نشر.
- سحب المستند يخفيه مستقبلًا دون حذف النسخة أو أثر النشر.
- واجهة العميل تستخدم استعلامات أو DTOs مخصصة، ولا تعرض الفريق كاملًا أو الحقول الداخلية.
- روابط التنزيل تصدر عند طلب التنزيل فقط، ومدتها الحالية 60 ثانية، ويسجل كل إصدار رابط في `document_access_events`.
- **Needs Client Confirmation:** مدة Signed URL النهائية في Production؛ القيمة الحالية القصيرة تقلل أثر مشاركة الرابط.

## الاحتفاظ والتدقيق

- لا يوجد Automatic Purge أو حذف نهائي في الـMVP.
- المشاريع والطلبات والعروض والعقود والمحادثات والماليات وسجل التدقيق محفوظة.
- الإخفاء يستخدم الأرشفة أو Soft Delete، و`deleted_at` لا يعني حذف الصف.
- ملفات المستندات لا تستخدم overwrite؛ لكل نسخة مسار Storage مستقل.
- الحسابات تعطل والموظفون يصبحون غير نشطين مع الاحتفاظ بنسبة الأعمال السابقة إليهم.
- Audit Log بنمط Append Only، ولا تمنح UPDATE أو DELETE للمستخدمين العاديين.
- **Needs Client Confirmation:** مدة الاحتفاظ القانونية النهائية وسياسة Legal Hold والحذف النهائي المؤجل.

## البيئة والتشغيل

- النشر المستهدف Vercel وSupabase مع مشاريع منفصلة للتطوير والاختبار والإنتاج.
- لا توضع مفاتيح Service Role أو SMTP أو `DATABASE_URL` في متغيرات `NEXT_PUBLIC_`.
- تهيئة أول Super Admin تتم بسكربت خادمي Idempotent يقرأ `INITIAL_SUPER_ADMIN_EMAIL`.
- التطوير يستخدم localhost وبريدًا تجريبيًا أو Mail Capture ولا يرسل للعملاء الحقيقيين.
- ملفات خرائط التقاضي والتركات مراجع تحليل داخل `docs/references` وليست أصولًا عامة.

## مسار ما قبل التعاقد المنفذ

- يبدأ العميل المسجل طلبًا من بوابته، ويظل الطلب `received` حتى يربطه مدير العملاء.
- بعد الربط يحدد مدير العملاء المنفذ والمعتمد، ثم يقدم المنفذ دراسة قابلة للإعادة وإصدار نسخة جديدة.
- العرض الفني والمالي مُرقم الإصدارات؛ قبول العميل أو طلب التخفيض أو التفاوض أو الرفض أحداث موثقة.
- لا يرسل العقد إلا بعد قبول عرض، ويخزن قبوله مع نسخة العقد وبصمتها وبيانات جلسة الموافقة.
- التحويل إلى مشروع Idempotent بقيد فريد على `service_request_id`، ويبدأ قالب التقاضي المنشور عند انطباقه.
- ملفات الطلب تحفظ في bucket خاص، ولا تعرض إلا عبر Signed URL قصير بعد اجتياز RLS.
- دورة المستند هي `draft` ثم `awaiting_approval` أو `published`، ويمكن نقل المنشور إلى `withdrawn` دون حذف الملف أو نسخته.
- النشر والسحب يحتاجان صلاحية `documents.publish`، بينما يسجل الرفع وتغيير الرؤية والتنزيل في سجلات دائمة.
- **Needs Client Confirmation:** قوالب النصوص القانونية النهائية للعروض والعقود، العملات المعتمدة، والمدة الافتراضية لصلاحية العرض.
