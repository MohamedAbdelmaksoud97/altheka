# تقرير شرح نظام أساس الثقة للعميل

## فكرة النظام

النظام هو منصة إدارية داخلية للمكتب القانوني. هدفه تنظيم دورة العمل من أول تسجيل العميل أو إنشاء ملفه، مرورًا بطلب الخدمة والدراسة والعرض والعقد، ثم التحويل إلى مشروع وتشغيله ومتابعته بالمستندات والمحادثات والمهام والاعتمادات والتقارير.

النظام ليس مخصصًا للتكامل مع ناجز أو المحاكم أو أي جهة خارجية. الموظف ينفذ الإجراء القانوني خارج النظام عند الحاجة، ثم يوثق النتيجة داخل النظام. لذلك يمكن اعتباره مصدر الحقيقة الداخلي للمكتب.

## المستخدمون والصلاحيات

يوجد نوعان رئيسيان من المستخدمين:

- العميل: يدخل على بوابة العميل ويرى فقط ما تم نشره له، مثل المستندات أو التقارير أو الإجراءات المطلوبة منه.
- الموظف: يدخل على Workspace، وما يظهر له يعتمد على دوره وصلاحياته ونطاق وصوله.

الأدوار المهمة:

- `super_admin`: مدير النظام، يملك صلاحيات واسعة لإدارة النظام والصلاحيات.
- `executive_manager`: المدير التنفيذي، يرى التقارير وسجل التدقيق والملفات الإدارية حسب الصلاحيات.
- `new_clients_manager`: مسؤول العملاء الجدد، يدير العملاء والطلبات والدراسات والعروض والعقود والتحويل لمشروع.
- `litigation_manager`: مدير إدارة التقاضي، يدير واعتماد مسارات ومشاريع التقاضي.
- `litigation_secretary`: سكرتير/مشغل التقاضي، يتابع التشغيل والفرق والمستندات حسب الصلاحيات.
- `estates_manager`: مدير التركات، يدير ملفات التركات والأصول والورثة والمالية والتقارير.
- `estates_secretary`: تشغيل ومتابعة التركات دون صلاحيات الاعتماد النهائية.
- `lawyer`: ينفذ المهام أو إجراءات التقاضي المسندة إليه ويرفع النتائج.
- `legal_specialist`: يعمل في نطاق قانوني مشابه حسب التكليف.
- `accountant`: يدير القيود المالية والمستندات المالية داخل التركات والمشاريع حسب الصلاحيات.
- `litigation_supervisor`: مشرف تخصصي يرى القضايا المطابقة لتخصصه ويمكنه إصدار لفت نظر داخلي.

المبدأ الأمني: كل عملية مهمة تمر بفحص الصلاحية ونطاق الوصول وحالة السجل، ويتم تسجيل التغييرات الحساسة في Audit Log.

## ما قبل التعاقد

هذا هو مدخل أغلب العمل.

الفلو الحالي:

1. مسؤول العملاء ينشئ أو يدعو العميل.
2. يتم تسجيل مصدر العميل، مثل واتساب أو تيك توك أو وسيط أو زيارة أو محامي أو أخرى.
3. ينشئ مسؤول العملاء طلب خدمة ويربطه بالعميل.
4. يحدد نوع الطلب: تقاضي، تركات، استشارة، أو غيره.
5. يتم رفع المستندات وربطها بالطلب.
6. يتم تعيين مكلف لدراسة الطلب.
7. المكلف يرفع الدراسة.
8. الدراسة تعتمد من الإدارة المختصة.
9. يتم إنشاء العرض الفني والمالي.
10. يتم إرسال العرض للعميل.
11. العميل يقبل أو يرفض أو يتفاوض.
12. عند القبول يتم إنشاء العقد.
13. بعد قبول العقد أو رفع نسخة موقعة يتم تحويل الطلب إلى مشروع.

مهم في الشرح: الطلب لا يتحول إلى مشروع إلا بعد قبول تعاقد صالح أو نسخة موقعة معتمدة.

## المشاريع

بعد التحويل يظهر المشروع في Workspace.

المشروع يحتوي على:

- رقم مشروع.
- نوع مشروع.
- حالة.
- عميل.
- مدير مشروع.
- مكلف رئيسي.
- أعضاء أو فرق.
- مستندات.
- محادثات.
- Workflow عند توفره.
- مهام تشغيلية.
- Audit للتغييرات الحساسة.

أنواع المشاريع التشغيلية المكتملة حاليًا:

- `litigation`: مشروع تقاضي.
- `estate`: مشروع تركة رئيسي.
- `estate_asset`: مشروع أصل تابع لتركة.
- `estate_litigation`: مشروع تقاضي تابع لتركة.

نوع `consultation` موجود كنوع طلب/مشروع، لكنه حاليًا ليس له خارطة Workflow تشغيلية منشورة. لذلك مشروع الاستشارة يدار كملف إداري بسيط بعد التحويل، وليس كمسار تشغيل كامل مثل التقاضي أو التركات.

## Workflow وخارطة السير

الـ Workflow هو خارطة السير الداخلية للمشروع.

عند تشغيل المشروع، يختار النظام القالب حسب نوع المشروع:

- التقاضي يستخدم `litigation-v2`.
- التركة الرئيسية تستخدم `estate-v2`.
- أصل التركة يستخدم `estate-asset-v2`.
- تقاضي التركة يستخدم `litigation-v2`.

كل Workflow يحتوي على مراحل وإجراءات. وكل إجراء له:

- اسم.
- حالة.
- تاريخ استحقاق.
- مكلفون.
- متابع أو معتمد.
- تحديثات.
- نسبة إنجاز.
- طلبات تمديد.
- مستندات أو نتائج.
- Audit.

من يبدأ خارطة السير؟

- من يملك صلاحية `workflow.start`.
- أو من يملك `system.override`.
- أو مدير المشروع.

مدير إدارة التقاضي `litigation_manager` يملك صلاحية `workflow.start` حاليًا. لكن تشغيل الخارطة لا ينجح إلا إذا كان نوع المشروع يدعم Workflow، مثل `litigation`. إذا كان المشروع `consultation` فلن يتم تشغيل خارطة سير لأنه لا يوجد قالب منشور للاستشارة.

## المهام التشغيلية

تمت إضافة صفحة مستقلة:

`/workspace/tasks`

هذه الصفحة تعرض المهام التشغيلية للمستخدم الحالي من:

- إجراءات الـ Workflow.
- إجراءات التقاضي.
- المهام المقترحة.

الفلاتر:

- مهامي.
- المتأخر.
- بانتظار اعتمادي.
- مهام مقترحة.
- مكتمل.

الموظف يستطيع من خلالها:

- إضافة تحديث على المهمة.
- تسجيل نسبة الإنجاز.
- طلب تمديد مع سبب.
- اقتراح مهمة جديدة.
- اعتماد أو رفض مهمة مقترحة إذا كان يملك الصلاحية.

لم يتم بناء نظام Tasks منفصل عن Workflow، لأن النظام يحتوي بالفعل على Workflow وإجراءات تشغيلية. لذلك تم تطوير الـ Workflow ليظهر كمهام واضحة بدل تكرار منطق جديد قد يسبب تضاربًا.

## التقويم

تمت إضافة صفحة مستقلة:

`/workspace/calendar`

التقويم يعرض:

- المواعيد الإدارية.
- الاجتماعات.
- جلسات التقاضي كمصدر قراءة إضافي.
- المواعيد المرتبطة بعميل أو طلب أو مشروع.

يدعم:

- عرض أسبوعي.
- عرض شهري.
- فلاتر للمواعيد والجلسات والمشاريع والطلبات.
- إنشاء موعد داخلي مع تحديد العنوان، الوصف، البداية، النهاية، المكان، الارتباط، والمشاركين.

لا يوجد تكامل مع Google Calendar أو Outlook في هذه المرحلة، لأن النظام مطلوب أن يظل داخليًا.

## الوكالات

تمت إضافة صفحة مستقلة:

`/workspace/powers-of-attorney`

تعرض الوكالات وتدعم:

- رقم الوكالة.
- العميل.
- المشروع أو الطلب المرتبط.
- تاريخ الإصدار.
- تاريخ الانتهاء.
- المستند المرتبط.
- ملاحظات.

الفلاتر:

- نشطة.
- قاربت على الانتهاء.
- منتهية.
- مرتبطة بمشروع.
- مرتبطة بطلب.

النظام يظهر تنبيهًا بصريًا للوكالات التي تنتهي خلال 14 يومًا.

## مسار التقاضي

مسار التقاضي مكتمل كنظام إداري داخلي.

يدعم:

- تسجيل بطاقة القضية.
- تصنيف القضية.
- تشغيل Workflow التقاضي.
- تحديد الإجراء القادم.
- بدء الإجراء.
- رفع نتيجة الإجراء.
- اعتماد النتيجة أو إرجاعها.
- تسجيل الجلسات.
- تسجيل نتيجة الجلسة.
- تحديد المسار التالي، مثل الاستئناف أو التنفيذ أو الإقفال.
- إضافة مكلفين مساعدين.
- إشراف تخصصي.
- لفت نظر.
- مستندات ومحادثات.

النقطة المهمة للعميل: المحامي لا يعتمد عمله بنفسه. هو ينفذ ويرسل النتيجة، والمدير أو صاحب الصلاحية يراجع ويعتمد.

## مسار التركات

مسار التركات شامل إداريًا.

التركة تبدأ كمشروع رئيسي `estate`.

داخلها يتم تسجيل:

- بيانات التركة.
- نوع التركة.
- الورثة والأطراف.
- الأنصبة.
- الحسابات البنكية.
- التحقق من الحسابات.
- الأصول.
- القرارات والموافقات.
- القيود المالية.
- التقارير الدورية.
- الفرق.
- التقاضي الفرعي عند النزاع.

كل أصل تركة يمكن أن ينشئ مشروعًا فرعيًا مستقلًا `estate_asset`. هذا يسمح بتشغيل أصل عقاري في مسار، وأصل آخر في مسار مختلف، دون تعطيل باقي التركة.

عند وجود نزاع يتم إنشاء مشروع `estate_litigation` مرتبط بالتركة وربما بالأصل المتأثر.

## موافقات الورثة

تمت إضافة موافقات الورثة كعملية مستقلة داخل ملف التركة.

داخل تبويب الموافقات والمالية يمكن:

- إنشاء طلب موافقة.
- تحديد نوع الطلب: عام، أصل، توزيع، تسوية.
- ربط الطلب بأصل عند الحاجة.
- تحديد تاريخ استحقاق.
- عرض حالة كل وريث:
  - لم يرد.
  - وافق.
  - رفض.
- تسجيل رد الوريث من جهة الإدارة.
- ربط الرد بمستند إقرار إن وجد.

تم الإبقاء على `estate_party_decisions` كسجل قرارات، ولم يتم استبداله.

## فرق التركات

الفرق تستخدم لتوزيع العمل داخل التركة والأصول.

أكواد الفرق الحالية:

- `inventory`: الحصر.
- `preparation`: التهيئة.
- `guardianship`: الحراسة.
- `liquidation`: التصفية.
- `marketing`: التسويق.
- `finance`: المالية.
- `litigation`: التقاضي.
- `reporting`: التقارير.

أدوار أعضاء الفريق:

- `leader`: قائد ومنفذ.
- `member`: عضو منفذ.
- `observer`: متابع فقط.

الفريق لا يشارك فعليًا في الإسناد إلا إذا كانت حالته `active`.

## المستندات

كل مشروع أو طلب يمكن أن يحتوي على مستندات.

المستند يمكن أن يكون:

- داخلي.
- ظاهر للعميل.
- يتطلب إجراء من العميل.

تمت إضافة:

- تصنيفات مستندات ديناميكية.
- فهرسة المستندات.
- رقم المستند.
- تاريخ المستند.
- وصف.
- عدد الصفحات عند توفره.

نشر المستند أو سحبه يحتاج صلاحية. العميل لا يرى المستند إلا إذا تم نشره له.

المستندات المهمة لا يتم حذفها نهائيًا. يتم التعامل معها بالأرشفة أو السحب مع Audit.

## المحادثات

كل مشروع يمكن أن يحتوي على:

- قناة عميل.
- قناة داخلية.

قناة العميل للتواصل الرسمي مع العميل.

القناة الداخلية للموظفين فقط.

الإشراف، لفت النظر، الاعتمادات الداخلية، وتفاصيل الفرق لا تظهر للعميل.

## المالية

النظام يدعم قيودًا مالية داخل التركات:

- إيراد.
- مصروف.
- احتياطي.
- توزيع.
- تحويل.

المحاسب أو صاحب الصلاحية ينشئ القيد ويرفق الدليل، ثم يرسله للاعتماد. مدير التركات أو صاحب صلاحية الاعتماد يوافق أو يرفض.

القيد المعتمد لا يتم تعديله مباشرة. التصحيح يكون بقيد عكسي أو إجراء لاحق.

## التقارير

يوجد نوعان من التقارير حاليًا:

1. تقارير التركات الدورية.
2. تقارير التشغيل العامة.

تقارير التركات:

- تقرير دوري كل 90 يومًا.
- يعتمد على بيانات الأطراف والأصول والماليات وحالة الإجراءات.
- يمكن إضافة ملاحظات بشرية.
- يمر بمراحل: مسودة، مراجعة، اعتماد، نشر، سحب.
- العميل لا يرى التقرير إلا بعد النشر.

تقارير التشغيل العامة متاحة في:

`/workspace/reports`

وتعرض:

- ملخص المشاريع النشطة.
- المهام المتأخرة حسب الموظف.
- المهام المتأخرة حسب المشروع.
- المهام بانتظار الاعتماد.
- المهام المقترحة بانتظار الاعتماد.
- لفت النظر المفتوح.
- تقرير أسبوعي مختصر.

هذه التقارير تشغيلية فقط، ولا تتضمن تقييم أداء مالي أو تقييم موظفين تلقائي.

## Audit Log

تمت إضافة صفحة عامة لسجل التدقيق:

`/workspace/audit-log`

تظهر فقط لمن لديه:

- دور `super_admin` أو `executive_manager`.
- وصلاحية `audit.read`.

الصفحة تعرض:

- من نفذ العملية.
- نوع العملية.
- الجدول المتأثر.
- رقم السجل.
- الوقت.
- IP أو Request ID إن وجد.
- البيانات قبل وبعد التغيير.

وتدعم فلاتر:

- الجدول.
- نوع العملية.
- المستخدم.
- من تاريخ.
- إلى تاريخ.
- عدد النتائج.

سجل التدقيق الكامل موجود في قاعدة البيانات داخل `private.audit_logs`، ولا يفتح مباشرة لباقي الموظفين أو العملاء.

## الإشراف ولفت النظر

في التقاضي يوجد مشرف تخصصي يرى القضايا المطابقة لتخصصه.

يمكنه إصدار لفت نظر على إجراء مفتوح لمكلف معين.

لفت النظر:

- داخلي.
- يحتاج سبب.
- يصل للمكلف والمدير.
- يمكن للمكلف الإقرار بالاطلاع والرد.
- لا يظهر للعميل.

## إدارة الموظفين

مدير النظام يستطيع:

- اعتماد موظف جديد.
- تحديد الإدارة.
- تحديد المسمى.
- تعيين الأدوار.
- تعطيل موظف.
- إعادة تفعيله.
- تعديل بياناته مع سبب.
- مراجعة الموظفين النشطين والمعلقين وغير النشطين.

كل تغيير حساس يتم تسجيله في Audit.

## مسار الاستشارة

الاستشارة موجودة حاليًا كنوع طلب ومشروع `consultation`.

لكن لا يوجد لها Workflow منشور في هذه المرحلة.

لذلك:

- يمكن تسجيل طلب استشارة.
- يمكن دراسته في ما قبل التعاقد.
- يمكن إرسال عرض وعقد.
- يمكن تحويله إلى مشروع.
- بعد التحويل يصبح ملفًا إداريًا بسيطًا.
- لا يتم تشغيل خارطة سير مثل التقاضي أو التركات.

إذا أراد العميل مسارًا كاملًا للاستشارات، يمكن إضافة قالب Workflow لاحقًا يتضمن:

1. فتح ملف الاستشارة.
2. جمع السؤال القانوني والمستندات.
3. دراسة المستندات.
4. إعداد الرأي القانوني.
5. مراجعة مدير الإدارة.
6. إرسال الرأي للعميل.
7. إغلاق الاستشارة.

## حدود النظام الحالية

النظام إداري داخلي.

لا يوجد:

- تكامل مع ناجز.
- تكامل مع المحاكم.
- تكامل مع Google Calendar أو Outlook.
- تقييم أداء موظفين تلقائي.
- تقارير مالية تحليلية متقدمة خارج البيانات التشغيلية المتاحة.
- Workflow منشور لمسار الاستشارة حتى الآن.

## طريقة شرح النظام للعميل

ابدأ بهذه الجملة:

“النظام ينظم دورة العمل الداخلية للمكتب من أول العميل الجديد حتى المشروع والتشغيل والمتابعة، مع صلاحيات دقيقة، مستندات، محادثات، مهام، اعتماد، وتقارير، وسجل تدقيق كامل للأثر.”

ثم اعرض النظام بهذا الترتيب:

1. تسجيل الدخول وحسابات المستخدمين.
2. لوحة الموظف Workspace.
3. طلبات ما قبل التعاقد.
4. الدراسة والعرض والعقد.
5. تحويل الطلب إلى مشروع.
6. مشروع التقاضي.
7. مشروع التركة.
8. الأصول والفرق.
9. المهام التشغيلية.
10. التقويم.
11. الوكالات.
12. موافقات الورثة.
13. المستندات والمحادثات.
14. التقارير.
15. Audit Log.
16. إدارة الموظفين والصلاحيات.
17. حدود النظام.

أهم نقطة تقولها بوضوح:

النظام لا يستبدل عمل الموظف القانوني، لكنه يمنع ضياع العمل، ويوحد المتابعة، ويحدد المسؤوليات، ويحفظ المستندات والقرارات والأثر التدقيقي.
