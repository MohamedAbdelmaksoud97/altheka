# محرك Workflow

## النموذج

- نشرت نسخ `litigation-v2` و`estate-v2` و`estate-asset-v2` للمشاريع الجديدة
  بتاريخ 2026-07-29 بعد اجتياز اختبارات المصدر. تظل النسخ المنشورة Immutable،
  وتبقى المشاريع القديمة على نسخها السابقة.
- القالب المنشور وإصداره غير قابلين للتعديل، ولا تتأثر المشاريع الجارية بإصدار
  جديد.
- يحتوي كل Action Template على المدة المخططة والأولوية والرؤية وقواعد الأطراف
  الأربعة والتبعيات وشروط البدء والإغلاق.
- تحل قواعد `role` و`job_title` و`project_membership` و`project_team` عند إنشاء
  Instance إلى مشاركين فعليين.
- يدعم المنفذ عدة أعضاء، بينما المسؤول والمتابع والمعتمد فرديون افتراضيًا.
- عدم معرفة المنفذ ينتج `awaiting_assignment` وفق قاعدة بدء المدة في القالب.

## التشغيل

- الأنواع: تلقائي، يدوي، مستمر، اختياري، مشروط، مرتبط بحدث، ودوري.
- أنواع التبعية تشمل `finish_to_start`, `finish_to_finish`, `start_to_start`.
- الإجراءات المستقلة تعمل بالتوازي ولا تجمع مددها.
- Critical Path يحسب التوقع ولا يغير المدد القانونية.
- لكل مرحلة `target_duration` و`maximum_duration`، ولكل إجراء `planned_duration`
  و`due_at`.
- تجاوز المدة ينشئ تنبيهًا وتصعيدًا ولا يغلق الإجراء أو المرحلة تلقائيًا.
- الانتقال والاعتماد والإعادة والتمديد والتجاوز وإعادة الفتح تمر بإجراء خادمي
  Transactional يسجل Audit.
- إجراءات متابعة القضية تستخدم دورة متخصصة: `planned` ثم `in_progress` ثم
  `awaiting_approval`، وبعدها `completed` أو `returned_for_revision`.
- لا يكمل المنفذ الإجراء بنفسه؛ يقدم نسخة نتيجة Append Only، ويعتمدها صاحب
  الصلاحية أو يعيدها. ينشئ الاعتماد الإجراء التالي المؤرخ ويحدث مؤشر القضية في
  Transaction واحدة.
- كل إعادة تنتج إصدار تقديم جديدًا، وتبقى التقديمات والمراجعات وروابط مستنداتها
  محفوظة ولا تقبل UPDATE أو DELETE.
- في مسار التقاضي لا يختار المحرك مرحلة اختيارية تلقائيًا. بعد اكتمال المرافعة
  الابتدائية أو الاستئناف أو التنفيذ، يكتمل العمل الحالي ويتوقف الـ Workflow عند
  `بانتظار تحديد المسار التالي`.
- يختار مدير المشروع أو مدير إدارة التقاضي أو `super_admin` الاستئناف أو
  التنفيذ أو الإقفال والتحصيل، مع سبب إلزامي. ينفذ الاختيار داخل Transaction
  ويسجل المرحلة السابقة والجديدة والسبب والمنفذ في Audit Log.
- يسمح بتغيير الإقفال والتحصيل غير المنفذ إلى مسار قضائي آخر، ولا يسمح بذلك
  بعد بدء إجراء إقفال فعلي حتى لا تضيع أعمال أو اعتمادات قائمة.

## الوقت والتكرار

- أيام العمل الافتراضية الأحد إلى الخميس، والعطلة الجمعة والسبت.
- المهام الداخلية بأيام العمل، والمواعيد القضائية والقانونية بتاريخها الفعلي.
- صلاحية العرض ثلاثة أيام تقويمية افتراضيًا.
- التنبيه الافتراضي: قبل 48 ساعة للمكلف، قبل 24 ساعة للمكلف والمتابع، عند
  التأخير لكليهما، بعد يوم عمل لمدير المشروع، وبعد ثلاثة أيام لمدير الإدارة.
- المدير التنفيذي لا يتلقى تصعيدًا يوميًا إلا عند قاعدة صريحة.
- يدعم التكرار كل 5 أو 7 أيام عمل، وكل 90 يومًا، والإنشاء بعد حدث بمدة محددة.
- تشغيل الـ Scheduler Idempotent عبر مفتاح فريد لكل Occurrence.

## ضمانات التقاضي والتركات

- لا تبقى قضية نشطة بلا `next_action` وتاريخ؛ يمنع الانتقال الذي يخرق القاعدة.
- لكل أصل تركة مشروع فرعي وWorkflow مستقل، ويمكن أن تعمل الحراسة والتقاضي
  والتصفية والتسويق بالتوازي.
- إغلاق مرحلة الحصر يحتاج الإجراءات الإلزامية أو استثناء معتمد.
- التقرير الدوري للتركة كل 90 يومًا، ويستحق خلال 15 يوم عمل من نهاية الفترة.

## حالات التشغيل

الإجراء يدعم `awaiting_assignment`, `blocked`, `ready`, `in_progress`,
`submitted`, `returned_for_revision`, `approved`, `completed`, `cancelled`.
وتسجل كل إعادة إسناد أو تغيير مدة أو رؤية أو حالة في Audit Log.

## الإسناد المتعدد ولفت النظر

- `project_assignees` هو سجل المكلف الرئيسي والمكلفين المساعدين مع تاريخ البداية
  والنهاية. تبقى `projects.primary_assignee_id` متزامنة للتوافق.
- `litigation_case_action_assignees` يسمح بعدة منفذين لإجراء القضية، بينما يبقى
  `assigned_to` قائد التنفيذ المتوافق مع الواجهات القديمة.
- عند إضافة مساعد، يضاف منفذًا إلى إجراءات القضية وWorkflow المفتوحة؛ وتزرعه
  Triggers في الإجراءات المستقبلية. كل تسليم يسجل المستخدم الفعلي.
- `project_attention_notices` يرتبط بإجراء Workflow أو إجراء قضية واحد فقط،
  ويتطلب إجراءً مفتوحًا ومكلفًا نشطًا. حالاته `sent` و`acknowledged`.
- عمليات الإسناد والإنهاء ولفت النظر والإقرار تمر عبر RPCs أمنية وتكتب Audit.

## تشغيل التركات

- `start_project_operational_workflow` يختار `estate-v2` للمشروع الرئيسي،
  و`estate-asset-v2` لمشروع الأصل، و`litigation-v2` لمسار تقاضي التركة.
- هوية الأصل جزء من Idempotency؛ إعادة طلب البدء تعيد نفس Instance ولا تنشئ
  Workflow مكررًا.
- علاقة Workflow بالأصل مستقلة عن ملكية صف الأصل للمشروع الرئيسي: المشروع
  الفرعي يملك Instance، بينما يظل الأصل مسجلًا تحت مشروع التركة.
- إنشاء أصل ينشئ مشروعه وقناتيه وينسخ فريق التركة ويبدأ Workflow الخاص به داخل
  العملية الخادمية.
- تقرير التركة الدوري له Schedule كل 90 يومًا، ويولد Snapshot موضوعيًا
  وإجرائيًا وماليًا في `project_report_versions`. لا يرى العميل النسخة إلا بعد
  انتقالها إلى `published`.

## فرق العمل التشغيلية

- الفريق ليس دورًا وظيفيًا ولا يمنح صلاحيات عامة؛ كل عضو يجب أن يكون عضوًا
  نشطًا في المشروع وتظل قدراته محكومة بـPBAC.
- قواعد الإسناد ذات `selector_type=project_team` تحل `project_team_code` إلى
  أعضاء الفريق النشط عند بدء Workflow وعند تغيير الفريق.
- `leader` و`member` المؤهلان فقط يصبحان منفذين. `observer` يتابع ولا يسند
  إليه تنفيذ.
- فرق مشروع التركة الرئيسي تمتد إلى مشاريع الأصول؛ تنشأ عضوية المشروع
  والمحادثة اللازمة قبل إسناد إجراءات الأصل.
- إضافة عضو أو تغيير قائد أو حالة أو مرحلة الفريق يعيد مزامنة الإجراءات
  المفتوحة فقط. الأعمال الجارية والمنجزة وتاريخ الإسناد لا يعاد كتابتها.
- الفريق `planned` لا يسند حتى يصبح `active`. إكماله أو إلغاؤه يوقف الإسناد
  المستقبلي ويعيد الإجراءات غير المبدوءة إلى انتظار الإسناد عند الحاجة.
