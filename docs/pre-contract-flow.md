# مسار ما قبل التعاقد

## الرحلة التشغيلية

1. ينشئ العميل المسجل طلبًا من `/client`.
2. يرفع العميل المستندات إلى Storage الخاص، وتحفظ بصمة SHA-256 لكل نسخة.
3. يفتح مدير العملاء الطلب من `/workspace/requests` ويربطه بملف العميل.
4. يحدد المدير المكلف بالدراسة ومعتمدها.
5. يقدم المكلف الدراسة، ثم يعتمدها المعتمد أو يعيدها للتعديل.
6. يرسل مدير العملاء العرض الفني والمالي.
7. يقبل العميل العرض أو يطلب تخفيضًا أو تفاوضًا أو يرفضه.
8. عند التخفيض أو التفاوض، يصدر المدير عرضًا جديدًا دون تغيير النسخ السابقة.
9. بعد قبول العرض، يرسل المدير نسخة العقد.
10. يعتمد العميل العقد، وتحفظ النسخة والبصمة والوقت والمستخدم وIP وUser Agent.
11. يحول مدير العملاء الطلب إلى مشروع، وتنفذ العملية مرة واحدة حتى عند تكرار الاستدعاء.

## الحالات

`received` → `linked` → `collecting_documents` أو `assigned` → `study_pending_approval`
→ `study_returned` أو `study_approved` → `proposal_sent`
→ `discount_requested` أو `negotiating` أو `proposal_accepted` أو `proposal_rejected`
→ `contract_sent` → `contract_accepted` → `converted_to_project`.

## الأمان والاحتفاظ

- كل تغيير تشغيلي يمر عبر RPC خادمية مسجلة في Audit.
- لا يملك `authenticated` صلاحية INSERT مباشرة على `service_requests`.
- يرى العميل الأحداث غير الداخلية والعروض والعقود الخاصة بطلبه فقط.
- المستندات المنشورة للعميل فقط هي التي تعبر سياسة RLS، وتصدر روابطها لمدة 60 ثانية عند طلب التنزيل.
- النشر والسحب يحتاجان صلاحية `documents.publish`، وكل إصدار Signed URL يسجل في `document_access_events`.
- لا تحذف بيانات الاختبارات القانونية؛ تؤرشف وتعطل حساباتها.

## اختبار القبول الحي

يشغل الاختبار على Supabase المرتبط ويستخدم حساب Super Admin من متغيرات البيئة:

```bash
npm run test:flow-live
```

ينشئ الاختبار حساب عميل مؤكدًا، ويمر بالرحلة كاملة عبر متصفحين، ثم يؤرشف البيانات ويعطل حساب الاختبار.
